# 插件 0.2.27 —— 一次戳回两条（忽略 bot 自身的戳事件）

日期：2026-10-02
版本：0.2.26 → 0.2.27
提交：`a9a09f8`（Gitee `0212fcc..a9a09f8`；GitHub 同区间，本机 `/root/_gitee_clone` 推）

## 现象

博士真机反馈：群聊里戳一次 → 回两条，**一条带人设、一条不带**。

## 排查（日志，决定性）

`docker logs astrbot --since 40m` 抓到同一时刻的两条入站戳事件，以及对应的两条回复：

```
10:28:25.626  2664648140/2664648140: [ComponentType.Poke]      ← 博士戳的
10:28:26.125  3825694788/3825694788: [ComponentType.Poke]      ← sender 正是 bot 自己
10:28:35.005  Prepare to send - 3825694788: 嗯？在呢，怎么了     ← 无角色口吻
10:28:35.322  Prepare to send - 2664648140: 哦呀，在呢。怎么了   ← 有角色口吻
```

- `3825694788` = 本 bot 的 QQ。第二条事件的发送者是 **bot 自己**。
- 成因：`on_poke` 判定「回戳」后会调 `send_poke` 把戳打回去，协议端把这次**出站动作回传成一条入站事件**（sender = bot），插件把它当成「有人又戳了我」，于是回了第二句。
- 两句口吻不同属正常：两条事件各自走一遍 `_poke_text`，模型各生成一句，随机性导致一句在角色内、一句退回通用腔（与 0.2.26 的口癖问题同源，不另处理）。

也就是说：**一次真人戳 → 插件回戳 → 回戳被回传成第二次「被戳」 → 多回一条。** 属协议端回环，不是模型问题。

## 改动

- `main.py` 的 `on_poke()`：取到 `uid` 后加守卫——
  ```python
  self_id = str(event.get_self_id() or "")
  if self_id and uid == self_id:
      return
  ```
  `event.get_self_id()` 返回 `message_obj.self_id`（`astr_message_event.py:199`）。
- 守卫位置在 `should_call_llm(True)` **之后**：即便第二条来自默认 LLM 管线，也会被一并掐掉，两种成因都覆盖。
- `metadata.yaml`：0.2.26 → 0.2.27。

## 校验

## 未验

- 真机再戳一次：确认只回一条。若仍回两条，说明还有第二条回环路径（如协议端把出站文本消息也回传），再据日志定位。

## 方法教训

- **「多回一条」先数入站事件，不要先怀疑模型**：日志里两条入站戳事件一眼可见，直接定位到回环；若只盯着模型会白查。
- **主动发出去的动作可能被协议端回传成事件**（戳、消息均可能）。凡是「收到 X 就回 Y」的处理器，都要防「Y 被回传成 X」的回环，最简判据是 `sender == self_id`。

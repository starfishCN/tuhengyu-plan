# 工作日志 · 2026-10-01 · 面板登录页（弃用 Basic Auth）

## 起因

用户截图反馈：**登录界面不好看**。截图内容是浏览器弹出的
`http://183.66.27.21:50505 要求提供用户名和密码` 原生对话框。

## 根因

原实现用的是 **HTTP Basic Auth**：

```python
@app.middleware("http")
async def _basic_auth(request, call_next):
    ...
    return _Resp(status_code=401, headers={"WWW-Authenticate": 'Basic realm="tuhengyu"'})
```

**那个框是浏览器画的，CSS 完全管不到。** 在深色面板上突然弹出一个系统样式的
白框，观感断裂。此外 Basic Auth 每个请求都要重发一次明文凭据。

## 方案：自建登录页 + HMAC 签名会话 Cookie

| 环节 | 做法 |
|---|---|
| 登录页 | 中间件直接返回**纯静态 HTML**（内联 CSS，不依赖 NiceGUI，不连 socket.io） |
| 会话凭据 | `tg_session` Cookie，值为 `HMAC-SHA256(sha256("tuhengyu|" + PANEL_PASS), "panel-session")` |
| 有效期 | 7 天，`HttpOnly` + `SameSite=Lax` |
| 密码比较 | `hmac.compare_digest`，用户名与密码**都比**（用 `&` 而非 `and`，避免短路导致耗时差异） |
| 改密码效果 | 密钥由 PANEL_PASS 派生 → **改密码 = 全部旧会话立即失效**，无需额外清理 |
| 登出 | 服务端 `/logout` 清 Cookie（前端必须整页跳转，SPA 路由不会发请求） |

### 放行边界（写错会「裸奔」或「自我锁死」）

```
/login  /logout            放行 —— 登录页本身是纯 HTML
/_nicegui/  （静态资源）   放行 —— 只有 JS / CSS / 字体，不含数据
/_nicegui_ws/ （实时通道） **必须带 Cookie** ← 关键
/favicon.ico               放行
其余一切                    必须带 Cookie，否则 303 跳 /login
```

## 本次最有价值的发现

**NiceGUI 的 socket.io 真实挂载点是 `/_nicegui_ws/`，不是 `/_nicegui/`。**

来源（nicegui 3.17.1 源码）：

```python
# nicegui/nicegui.py:53-54
sio_app = SocketIoApp(socketio_server=sio, socketio_path='/socket.io')
app.mount('/_nicegui_ws/', sio_app)
```

坑在于：**`"/_nicegui_ws/".startswith("/_nicegui/")` 是 `False`** ——
`_nicegui_ws` 与 `_nicegui/` 是两个不同前缀。所以：

- 如果只写 `/_nicegui/` 前缀放行，实时通道**会落到最后的兜底分支**（要求 Cookie）——
  行为上是对的，但**不是靠显式保护做到的**，将来 NiceGUI 若改路径就会破。
- 第一版我把它写成 `if path.startswith("/_nicegui/"): if "socket.io" in path: ...`
  —— 这是**死代码**：`/_nicegui_ws/...` 根本进不了这个分支。

**已改为显式判断 `/_nicegui_ws/` 前缀**，并注明理由。

## 踩坑记录（可复用）

1. **`ssh 'cat > file' < localfile` 会挂死**：stdin 重定向与 `sshpass -p` 的 TTY
   分配冲突，命令超时不返回，且**远端什么都没做**。→ 改用 `scp -P <port>`。

   因为 service 文件里可能写成 `Environment="PANEL_PASS=xxx"`。
3. **测试脚本写成文件再 scp 执行**，比在 ssh 单引号里塞复杂命令可靠得多
   （引号嵌套是主要故障源）。

## 追加 2：动画没效果的排查与修正

用户反馈「没看出来有浮现效果」。commit `c9642e6`。

### 诊断（脚本 `archive/diag_render.sh`）

关键输出：

```
html 里出现 <div class="tg-  的次数: 0
出现 id="app" 的次数: 1
```

**面板是客户端渲染（CSR）。** 初始 HTML 里只有 `<div id="app">`，界面全部由 Vue 构建。
之前 grep 到的 `tg-main` / `tg-brand` **只在 CSS 里**，不是真实 DOM。

### 根因

CSS `animation` 在元素**插入 DOM 时即开始计时**，而 NiceGUI 在数据到达前会隐藏容器
—— **动画在元素还看不见的时候就跑完了**。等页面真正显示，它已停在终态。
所以「没看出来」是真的没播，不是用户没注意。

### 修正

- 弃用 `animation`，改为 `transition` + `.tg-in` class
- 初始态：`html:not(.tg-in)` 时 `opacity:0` + `translateY(28px)`
- 触发：新增 `ENTER_JS`，轮询 `.tg-main` 出现**且 `offsetParent !== null`**（真实可见）
  → 等两帧 → 加 `.tg-in`
- 兜底：3 秒后 `tg-force` 动画强制显示（绝不让面板空着）
- 参数放大：位移 12→28px、时长 .5→.6s、错开间隔 .07→.08s

### 为什么用轮询而不用 MutationObserver

轮询 40ms 一次、最多 80 次（3.2s），对这种一次性场景足够，
且比 observer 更容易加超时兜底。

### 验证限制（重要）

**无法在无头环境验证渲染效果。** 已验证的只是「规则和脚本确实注入了 HTML」：
`tg-in` ×10、`tg-force` ×2、`transition-delay` ×7、`documentElement` ×1、
`offsetParent` ×1、旧 `tg-enter` 残留 0。首页字节 27454 → 29056。

实际观感、以及触发时机是否准确，**必须由用户实机确认**。

### 下次若仍无效果，排查顺序

1. 系统是否开了「减弱动态效果」—— 我们的 CSS 会据此禁用动画（设计行为，不是 bug）
2. 浏览器缓存 —— 用无痕模式复验
3. 若出现「空白数秒后突然出现」→ `ENTER_JS` 轮询失败、走了 3 秒兜底，需修

## 追加 3：v3 倒带式重播 + 移除 reduce-motion 保护

用户第二次反馈「还是没有」。commit `a1c9450`。

### 第二轮诊断（关键）

回看三代代码，**每一代都写了同一段**：

```css
@media (prefers-reduced-motion: reduce) { ... 动画禁用 ... }
```

**如果用户系统开着「减弱动态效果」，这三代全都不会有效果。**
这个假设能一次性解释全部失败，且与 v1 / v2 / v3 的失败表现完全一致。

**处理**：移除该保护（CSS 的 media 查询 + JS 的 matchMedia 检查）。
理由：私有部署、用户明确要求该视觉反馈，观感优先。
注释里保留说明与恢复方法。

### v3 机制：倒带式重播

不再依赖「元素何时可见」这个不可控信号：

1. CSS 里**不设初始隐藏** → 元素先正常显示（因此**不存在空白面板风险**）
2. JS 轮询 `.tg-main` 存在 + `readyState !== 'loading'` + `getBoundingClientRect().height > 0`
3. 满足后等 400ms → 用内联样式打回起点（`opacity:0` + `translateY(36px)` + `transition:none`）
4. 强制重排 → 两帧后清空内联样式 → transition 必然播放

### 对照实验设计

登录页的 `@media (prefers-reduced-motion: reduce) { .card { animation: none } }`
**刻意保留未动**。于是形成天然对照：

- 系统开了 reduce motion → 登录页**无**淡入、面板**有**动画
- 系统没开 → 两边都应正常

**这个对照能一次性判定假设是否成立。**

### 实测

`prefers-reduced-motion` 字符串残留 3 处 —— 均在**注释里**（说明文字 + 示例代码），
非生效代码。`matchMedia` 0、`rewind` 2、`getBoundingClientRect` 2、`readyState` 1、
`style.opacity = '0'` 1、`transition` 1、`delay` 7。首页字节 29056 → 30288。

### 若仍无效的 Plan B

不再依赖前端时序，改用**服务端可确认的信号**：
`app.on_connect`（客户端 socket.io 连上时由服务端触发）→ `ui.run_javascript()` 下发放行指令。
socket 连接建立是「页面确实活了」的服务端可见证据，比前端轮询可靠。

## 追加 4：修掉「先闪一下」+ 放缓节奏

用户反馈：「有了，但是是先闪一下完整的再显示动画，而且动画太快了」。commit `f966b8c`。

### 问题 1：先闪一下（v3 的机制缺陷）

v3 的「倒带式重播」**必然**导致这个：元素先正常显示（终态），
400ms 后才被内联样式打回起点重播 —— 中间那段就是用户看到的「完整内容」。

**这不是调参能救的，是机制错了。已废弃。**

### 问题 2：太快

两个原因叠加：

- 时长 0.6s 偏短
- 曲线 `cubic-bezier(.22,1,.36,1)`（easeOutQuint）**起手就冲完大部分位移**
  → 主观上很「急」

### 修正：回到 v2 机制，但修掉它的缺陷

| 项 | v3 | 现在 |
|---|---|---|
| 机制 | 倒带重播 | 初始隐藏 + 检测放行 |
| 时长 | 0.6s | 0.8s |
| 曲线 | `cubic-bezier(.22,1,.36,1)` | `cubic-bezier(.16,.84,.44,1)` |
| 位移 | 36px | 24px |
| 卡片错开 | 0.08s | 0.1s |

**关键**：元素**从插入 DOM 起就是透明的**（`html:not(.tg-in)`），所以不存在
「完整内容」阶段 → 不会闪。JS 只在 `getBoundingClientRect().height > 0`
（确实渲染出来了）之后加 `.tg-in`。

同时**移除**了 v2 里的「超时提前放行」（`tries > 80` 时 fire）—— 那会在元素
出现前就放行，等于取消动画。现在脚本若没跑，由 CSS 的 3 秒兜底（`tg-force`）
负责显示，不会把面板锁在透明状态。

`rewind` 0、`style.opacity` 0、`tg-in` 6、`html:not(.tg-in)` 4（初始隐藏 2 + 兜底 2）、
`tg-force` 2、`classList.add('tg-in')` 1、`getBoundingClientRect` 1、
`.8s cubic-bezier` 2、`transition-delay` 7。首页字节 30288 → 29544。

### 四代失败的真凶清单（记下来，避免重蹈）

1. **v1**：用 CSS `animation` —— 客户端渲染下，动画在元素不可见时就播完
2. **真凶一（贯穿 v1–v3）**：`@media (prefers-reduced-motion: reduce)`
   —— 用户系统开着「减弱动态效果」，把动画整个关掉。**已移除。**
3. **真凶二（v2）**：超时提前放行，在元素出现前就加 class
4. **v3 的机制缺陷**：倒带必然先闪完整内容

### 教训

这四轮最该早点做的一件事：**先花一次工具调用确认「HTML 是 SSR 还是 CSR」**。
那一条信息能直接否掉 v1、并让 v2 的方向一开始就是对的。
后面三轮都是在为「没做这一步」还债。

## 一、设置页「老问题」复发：真正根因是 BOM

**症状**：「设置」页签报「读不到配置结构（`_conf_schema.json`）」，配置项一个都不渲染；其余页签正常。

**排查（真机日志直证）**：VPS 上 `astrbot` 容器日志连续刷

```
[web.settings:42] [图恒宇] 读取 _conf_schema.json 失败：
Unexpected UTF-8 BOM (decode using utf-8-sig): line 1 column 1 (char 0)
```

13:15 与 14:59 各多轮。与 0.3.1 的旧因（`PLUGIN_ROOT` 基准落进 `web/`）**不同**：这回路径是对的，卡在**编码**。

**根因**：`_conf_schema.json` 文件头带 UTF-8 BOM（`EF BB BF`）。
`json.load(open(..., encoding="utf-8"))` 遇 BOM 直接抛异常 → `except` 吞掉 → 返回 `{}` → 前端 `renderSettings` 走「读不到配置结构」分支。

- 已验证：全仓 BOM 扫描，**只有这一个文件**带 BOM。
- 未知：BOM 具体由哪一环写入（推测为带 BOM 的编辑器 / 复制粘贴链）。

**修法（两层）**：

1. **数据层**：`_conf_schema.json` 去 BOM（重写为无 BOM UTF-8）。解析通过，12 个顶层键。
2. **代码层**：所有「读可能被手改的 json」改用 `encoding="utf-8-sig"`（utf-8-sig 读无 BOM 文件同样正常）。
   写盘仍用 `utf-8`，**不写 BOM**。
   涉及：`web/settings.py:39`、`core/favour.py:340/598/670`、`core/schedule.py:130`、
   `handlers/proactive.py:42`、`diag/token.py:56`。

**为何 0.3.1 没防住**：0.3.1 只修了「路径基准」，`except` 吞异常 + 只打 `warning` 的设计没变，
所以换一种坏文件照样复发。这次把「读法」改成容错，同类复发面收窄。

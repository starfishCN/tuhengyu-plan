# 插件 0.3.0 / 0.3.1：main.py 模块化拆分（2026-10-02）

## 结论

自检报告里的 C1–C3 一次做完。`main.py` 从 1396 行降到 183 行，**12 个 handler 与 10 个 Web 路由的注册数与拆分前完全一致**，业务逻辑一行未改。

## 做法

- **机械搬移**：脚本按「装饰器 + def」切块，逐块搬到新文件，外面套一层 `class XxxHandlers:`，主类改为多继承组装。不手抄，避免抄错。
- **可行性先验证再动手**：读 AstrBot 源码 `/AstrBot/astrbot/core/star/`，确认三件事——
  1. `@filter.*` 装饰器在**模块导入时**执行注册（`get_handler_or_create` → `star_handlers_registry.append`），所以带装饰器的方法放子模块照样注册；
  2. `handler_module_path` 取 `handler.__module__`，卸载判据是 `_is_plugin_module_path`：`module_prefix = "data.plugins.<插件目录>"`，子模块路径 `startswith(prefix + ".")` 成立；
  3. `__import__(path, fromlist=[module_str])` 走正常包导入，子包可用相对导入。
  结论：mixin 方案成立，**不需要转发层**。
- **可重复执行**：`scripts/split_main.py` 每次先从 `archive/main.py-0.2.28.bak` 还原再拆；`scripts/verify_split.py` 做守恒校验。

## 踩到的坑

1. **相对导入层级**。`commands.py` 在包根，`from ..core` 会多退一层变成 `data.plugins.core`，报 `ModuleNotFoundError: No module named 'data.plugins.core'`，插件一度加载失败。规则：包根文件用 `from .core.x`，子目录文件（`handlers/` `web/` `diag/`）用 `from ..core.x`。首版脚本对所有文件统一加深度，是错的。
2. **小节注释归属**。`# ---------- xxx ----------` 这类注释要归给**下面**的成员，否则每个拆出文件的末尾都会挂一条属于下一个模块的注释。

## 回归：设置页读不到 schema（0.3.1 修复）

上线后真机首次打开插件页即命中：**「设置」页签报「读不到配置结构（_conf_schema.json）」，配置项一个都不渲染**。
同时「状态 / 操作 / 表情包」三个页签正常 —— 只有设置页拿不到 schema。

- **根因**：`_load_schema` 搬进 `web/` 后，仍用 `os.path.dirname(os.path.abspath(__file__))` 定位插件内文件，
  于是去找 `web/_conf_schema.json`，文件不存在 → `except` 吞掉异常 → 返回 `{}`。
  容器日志直证：`[web.settings:37] 读取 _conf_schema.json 失败：[Errno 2] No such file or directory: '.../web/_conf_schema.json'`。
- **这类坑的判据**：拆分后，凡是用 `__file__` 推算「插件内某个文件」的代码，基准都会变。
  本次已全量自查，`__file__` 只有 3 处：本处（错）、`core/scheduler.py` 的 `parent.parent`（core 深度未变，正确）、
  `main.py` 的兜底数据目录（main 仍在根，正确）。其余取路径一律走 `self._data_dir()`，不受影响。
- **修法**：`web/settings.py` 顶部加 `PLUGIN_ROOT = os.path.dirname(os.path.dirname(os.path.abspath(__file__)))`，
  路径基准改用它；同一段补丁并进 `scripts/split_main.py`，重跑拆分脚本不会再犯。
- **验证**：`scripts/schema_check.py` 在容器内直接调用 `_load_schema`，返回 12 个顶层键
  （`enabled` / `persona_id` / `persona_prompt` / `chat_private` / `chat_group` / `schedule` / …），`PLUGIN_ROOT` 指向插件根。
- **留档说明**：此前**无同类记录** —— 症状关键词「读不到 / 配置结构 / schema 为空」在 `logs/` 与项目 README 中 0 命中，
  这是拆分引入的首次回归，已补入本节。
- **教训（写进 checklist）**：模块搬家时，凡 `__file__` 参与路径计算的，逐个复核基准深度。

## 回归：全插件 handler 静默失效（0.3.6 修复）

**症状**：真机发 `/图恒宇好感`、`/图恒宇自检` 等命令**无任何回执**；戳一戳、表情包、群聊主动插话、好感注入一并不响应，消息全被 LLM 接走。日志无 traceback、无告警 —— **静默**。

**排查（四路交叉）**
- 静态走查：`core/star/star_manager.py`（加载期实例绑定）、`core/star/star_handler.py`（`only_activated` 检查）、`core/pipeline/waking_check/stage.py`（唤醒判定）、`core/star/session_plugin_manager.py`。
- 运行时面板 API：`/api/commands` 显示本插件命令**已注册且 enabled** —— 掩盖了问题（注册成功 ≠ 生效）。
- 容器内反向 WS 事件注入：带 token 往 `ws://127.0.0.1:6199/ws/event` 注入 `/图恒宇好感`，复现无回执。
- 运行时探针：往 `waking_check/stage.py` 插入日志打印 `star_map` —— 里面**只有主模块**，本插件 handler 全在子模块，查找不到。

**根因**：0.3.0 拆分把带 `@filter.*` 的方法搬进 `handlers/`、`commands.py` 等子模块，`handler.handler_module_path` 随之变成子模块名。AstrBot 有两处按它**精确匹配**：
1. `waking_check` 阶段用 `star_map[module_path]` 判定 handler 归属哪个插件，查不到即当「未激活插件」**整体跳过**；
2. 加载期只对 `module_path == 插件主模块` 的 handler 做实例绑定（`functools.partial(raw, star_cls)`）。
子模块 handler 两条都不满足 → 既被判未激活、又没绑实例，调用时缺 `self` / 缺 `event`，于是全插件行为一起失效（不是某个命令的问题）。

**修法（`main.py` 新增 `_bind_submodule_handlers()`，在 `initialize()` 首行调用，可重复执行）**
1. 把本包已加载子模块路径别名到主模块 metadata，补 `star_map` 查找；
2. 把子模块 handler 的 `module_path` 归一到主模块，并用 `functools.partial(raw, self)` 绑到本实例，补实例绑定。
新增带 `@filter.*` 的方法放在任一 mixin 里会被自动收编，无需额外处理。

**验证（真机注入）**

| 输入 | 结果 |
|---|---|
| `/图恒宇好感` | `[图恒宇] 好感度 0｜印象：中立｜关系：陌生人` |
| `图恒宇好感`（无斜杠） | 同上 + 附表情包（证明 `on_decorating_result` 钩子恢复） |
| `/图恒宇` | `[图恒宇] 调度器运行中。` |
| 容器日志 | 无 `TypeError`；`生活调度器已启动` / `AstrBot started` 正常 |

**教训**
1. **handler 注册 ≠ handler 生效**。注册在导入期完成（所以面板 `/api/commands` 看得到），激活与实例绑定在加载期按 `module_path` 精确匹配 —— **查注册列表会漏判**，必须看运行时行为或 `star_map`。
2. mixin 复用代码没问题，但 `@filter.*` handler **不能只靠继承**；跨模块注册时要显式把 `module_path` 与实例归位。

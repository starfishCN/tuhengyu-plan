# 表情包「单独发」的时序依赖 —— 实测结论：不成立，不改

日期：2026-10-02
状态：已实测 / 结论为「不改」/ 无代码改动

## 原疑点（todolist 第 4 条，P3，推测）

`handlers/sticker.py` 的 `send_sticker_separately()` 挂在 `@filter.after_message_sent()`。
怀疑：该钩子在回复已发出之后才触发，此时 `event.get_result()` 可能已被清空 → 选图拿不到回复正文，
退化成只按「此刻状态」选图（`_sticker_reply_b64` 有 `reply_text=""` 兜底，所以不报错、只是选图变差）。

## 结论

**猜想不成立。** `after_message_sent` 阶段 `event.get_result()` 仍然有效，选图能拿到本条回复正文。**不改代码。**

## 依据一：AstrBot 源码（决定性）

`/AstrBot/astrbot/core/pipeline/respond/stage.py` 末尾：

```python
if await call_event_hook(event, EventType.OnAfterMessageSentEvent):
    return
event.clear_result()          # ← 在钩子之后才清
```

即顺序是 **先跑 `after_message_sent` 钩子 → 再 `clear_result()`**。

补充查证：全仓 `clear_result()` 共 7 处，respond 阶段这一处（stage.py:331）是消息发送链路上唯一会清 result 的点，
且它在钩子之后；`process_stage/star_request.py` 的两处是「清上一个 handler 的结果」，在更早阶段。

另外确认本轮不存在旁路：`cmd_config.json` 里 `streaming_response: false`，
所以响应不会走 `respond/stage.py` 中那个「流式结果直接 return」的分支（该分支确实会跳过 `after_message_sent`）。

## 依据二：插件侧行为实测

在测试机容器内、按 AstrBot 的真实包名 `data.plugins.*` 导入 `handlers.sticker`，
用假 event 直接调 `StickerHandlers._sticker_reply_b64`，记录它传给 `pick_sticker` 的上下文：

```
[正常 result]      选图上下文=['哼，我才不理你在家闲着']
[result 抛错]      选图上下文=['在家闲着']
[概率 0]           选图上下文=[]
```

- 正常时：回复正文（`哼，我才不理你`）确实进入了选图上下文，后接当前场景/状态（`在家闲着`）。
- result 不可用时：按设计回退为「只按状态」，不崩。

## 影响面 / 遗留

- 行为符合设计，无需修改。
- **已知限制（不在本轮范围）**：若日后把 `streaming_response` 打开，`respond/stage.py` 会在流式分支提前 `return`，
  不触发 `after_message_sent`，于是「单独发」与「回复后附」两条表情包路径都不会执行。
  当前配置为 `false`，不触发；若将来要开流式，需一并处理。

# 2026-10-03 · Gitee 451 拦截与面板密码策略

## 一、Gitee 拦了一键安装脚本

**现象**：在目标机上执行教程首句命令：

```
curl: (22) The requested URL returned error: 451
```

**排查**（本机复测，排除机器因素）：

| 请求 | 结果 |
|---|---|
| `raw/main/install.sh` | **451** `The content may contain violation information` |
| `raw/main/README.md` | 200 |
| `raw/main/LICENSE` | 200 |
| `raw/main/tutorial/README.md` | 200 |
| `raw/main/panel/install.sh` | 404 |
| `api/v5/.../contents/install.sh` | 200（内容可读，base64） |

**结论**：Gitee 风控只命中 `install.sh` 这一个文件，不是仓库问题、不是网络问题。
同仓其他文件正常，走 API 也能取到内容。

**处置**：改名 `install.sh` → `setup.sh`（方案 A）。
根因不明，改名不保证永久生效，若再次被拦需转方案 B（Gitee 工单）。

## 二、仓库里躺着明文默认密码

`panel/install.sh` 第 65 行打印 `默认账号：admin / <已废弃的固定明文>`，
而它会被发布到仓库根目录对外；`panel/deploy/tuhengyu-panel.service`
第 9 行 `Environment=PANEL_PASS=<已废弃的固定明文>` 同样是明文，且这个文件在公开仓。

面板能执行任意系统命令（装 Docker、改 daemon.json），
固定密码 + 公网暴露 = 谁扫到谁进。同时违反「公开产物不留凭据」。

**处置**：改成三段式。

1. `setup.sh` 安装时用 `/dev/urandom` **随机生成** 16 位初始密码，
   `sed` 写进 service 文件，只在安装终端打印一次；不写进仓库。
   （想自己指定：`PANEL_PASS='xxx' bash setup.sh`。）
2. `deploy/tuhengyu-panel.service` 的密码位改为占位符 `__PANEL_PASS__`。
3. `main.py` 新增**首次登录强制改密**：

| 项 | 说明 |
|---|---|
| 存储 | 面板目录 `.panel_auth.json`（0600），`盐 + SHA-256` |
| 门禁 | 未设置过 → 除 `/set-password`、`/logout` 外一律 303 押过去 |
| 会话 | `_session_token()` 由密码派生 → 改密即踢掉所有旧会话 |
| 最短长度 | 8 位 |
| 回退 | 忘密码删 `.panel_auth.json` 重启，回到 service 里的初始密码 |

## 三、验证

`/tmp/test_panel_auth.py`（桩掉 nicegui / fastapi / httpx，只测认证与改密），
15 项断言，**14 项 PASS**：

- 未改密 → `_must_change()` 为真；改密后为假
- 初始密码可登录；错密码、错用户名被拒
- 改密后：新密码可登、旧密码立即失效、会话密钥轮换
- 密码文件不含明文
- 登录页 / 改密页无残留占位符，表单 action 正确

唯一 FAIL 是 `auth 文件权限 600` —— 实测 `/sdcard` 是 FUSE 挂载，
`chmod` 不生效（一律 660），`/tmp` 上同样代码得 600。
**属测试环境限制，非代码问题**，真机（ext4）应为 600。

`bash -n panel/setup.sh`、`python3 -m py_compile panel/main.py` 均通过；
`sed` 替换占位符已单测。

## 五、遗留

- **发布仓需手动改名**：远端根目录的 `install.sh` 要删掉、换成 `setup.sh`。
- Gitee 451 是否会再次命中，改名后需复测。
- 已部署的旧面板（无 `.panel_auth.json`）升级后会立刻进入强制改密流程，
  这是预期行为；但服务文件里若仍是旧明文密码，改密后即被 `.panel_auth.json` 取代。

## 一、戳一戳概率化

### 结论

「回戳」与「回话」拆成两件独立的事，各自掷骰：可能只回戳、只说话、两样都做、或干脆不搭理。

### 依据

原实现里普通关系「必答一句」，关系好「回戳 + 多数补一句」——每被戳都必有反应，不像人。

### 改动

`core/poke.py` 的 `decide()`：

- 新增参数 `speak_prob`（默认 0.75）。
- 分档改为两组概率：

| 档位 | 回戳 back_p | 回话 speak_p |
|---|---|---|
| 关系好（≥40） | 0.70 | 0.90 |
| 普通 | `poke_back_prob`（0.6） | `speak_prob`（0.75） |
| 关系差（<-10） | 0.15 | 0.30 |

- 两掷结果组合：都中 → `BOTH`；只中回戳 → `SILENT_POKE`；只中回话 → `TEXT`；都不中 → `IGNORE`（reason 记「·这次没理」）。
- 冷却 / 连戳 / 睡着 三条前置分支不变。

`main.py` 的 `on_poke` 读取 `speak_prob` 并传入；`IGNORE` 时补一条 INFO 日志（冷却除外，避免刷屏）。

`_conf_schema.json`：`poke` 的 hint 重写为概率口径，`poke_back_prob` 描述改为「回戳的概率」，新增 `speak_prob`（默认 0.75）。

### 概率实测（离线 4000 次采样）

- 普通关系：`both 0.447 / text 0.304 / silent_poke 0.153 / ignore 0.097`
- 关系好：`both 0.636 / text 0.266 / silent_poke 0.072 / ignore 0.026`
- 关系差：`ignore 0.599`

## 二、token 诊断

### 结论

移植回 `/token诊断` 指令，输出最近一次 LLM 请求的构成与今日累计用量。

### 依据

字段取自 AstrBot 源码（容器内核对）：`ProviderRequest` 有 `system_prompt` / `contexts` / `func_tool(ToolSet)` / `model`；`LLMResponse` 有 `usage: TokenUsage`（`input_other` / `input_cached` / `output`）。

### 改动

`main.py` 新增：

- `_tok_snapshot(event, req)`：在 `on_llm_request` 里记下 system_prompt 字符数、上下文条数与字符数、工具数（每个工具的 name+description+parameters 字符数，降序）、prompt 字符数；并累计今日请求数与输入估算。
- `_tok_output(resp)`：在 `on_llm_response` 里累计输出 token（有 `usage.output` 用真值，否则按回复字符估）。
- 折算口径 `_TOKEN_CHARS = 2.06`（实测 7994 字符 ≈ 3876 token）。
- 统计存 `data/plugin_data/astrbot_plugin_tuhengyu/token_stats.json`，按日期自动归零。
- 命令 `@filter.command("token诊断")`。

### 输出样例（格式）

```
[图恒宇] token 诊断（最近一次请求 09:20:11，模型 (默认)）
system_prompt：7994 字符 ≈ 3880 token
上下文：3 条 / 786 字符 ≈ 382 token
工具：18 个 / 9052 字符 ≈ 4395 token
本次合计 ≈ 8657 token
今日：私聊 12 次，输入 ≈ 93210 token
　　　全部 15 次，输出 ≈ 13210 token
工具明细（前 6）：find_music≈417、send_message_to_user≈417、...
```

## A. Bug / 健壮性隐患

### A1 设置保存静默失败（已验证）
`main.py:1357-1363`：
```python
self.config.update(merged)
save = getattr(self.config, "save_config", None)
if callable(save):
    save()
```
`save_config` 不存在或抛异常被外层吞时，接口仍返回 `{"ok": True}`。用户以为存了，实际没落盘。
**修法**：`callable(save)` 为假时返回 `error_response("配置对象不支持保存，请用 AstrBot 官方设置页", 500)`；或至少在响应里带 `saved: false`。

### A2 数值字段被清空即写 0（已验证）
`main.py:1256-1274` `_coerce`：
- `int` / `float`：`int("")` 抛异常 → 返回 `0` / `0.0`。用户在前端把一个数值输入框清空，保存后该字段变 0，而非回落 schema 默认值。
- `bool`：非真值串一律 `False`。若某个默认 `true` 的字段被传空串（`""`），会被判 `False`，与默认相反。
**修法**：空串/None 时返回默认值（`sch.get("default")`），不要落 0。

### A3 单独发表情包依赖 after_message_sent 的 result（推测）
`main.py:228-231`：`event.get_result()` 在 `after_message_sent` 阶段是否仍返回有效结果，取决于 AstrBot 内部清理时机。当前有 `try/except` 兜底，最坏退化为 `reply_text=""`，只影响选图精度，不报错。风险低，但建议改为「在 `on_decorating_result` 阶段把该条的选图结果暂存，`after_message_sent` 只负责发送」，消除时序依赖。

### A4 识图归类失败被静默计入「留在其他」（推测）
`page_sticker_classify`（`main.py:1206-1215`）调 `classify_image`；`core/classify.py` 失败时返回 `FALLBACK`，于是 `kept += 1`。用户看到的是「留在其他 N 张」，看不出其实是模型调用失败。
**修法**：`classify_image` 区分「判不出类目」与「调用失败」，后者单独计入 `failed` 并回传原因。

### A5 自动收集不区分来源（未知）
`collect_sticker`（`main.py:249-283`）对所有入站图片收集，单条上限 2 张。是否会收到 bot 自己发出的表情包（回环，同 0.2.27 poke 的成因）尚未实测。
**待验**：发一张图给 bot、bot 回一张表情包，看 `collected/` 是否多出 bot 自己那张。若会，加 `sender == self_id` 过滤。

### A6 识图归类用默认 provider（已验证）
`main.py:1187`：`provider = self.context.get_using_provider()`。用的是 AstrBot 默认对话模型，不是 `schedule.generate_model` 之类可配置项。若默认模型不支持多模态，归类必然全失败（且按 A4 表现为「留在其他」）。
**修法**：归类走一个可配置的 provider（复用现有 `select_provider` 机制），或至少在校验阶段提示「当前模型可能不支持识图」。

## B. 冗余

### B1 表情包两条路径逐行重复（已验证）
`attach_sticker`（167-204）与 `send_sticker_separately`（207-245）前 26 行几乎完全相同：取配置 → 判 enabled → 判 send_separate → 掷骰 → 取 reply_text → `state_at` → `pick_sticker` → `read_base64`。差异仅在最后「append 到 chain」vs「单独 send」。
**修法**：抽 `_pick_sticker_for(event) -> str | None`（返回 base64 或 None），两条路径各自只保留「发」的一段。

### B2 函数内 import 散落 20+ 处（已验证）
grep 结果：`import os` 出现在 148/267/547/554/804/820/1236 行；`import json` 出现在 553/575/819/840/1235/1248/1277 行（另有 `json as _json` 870）；`import time as _time` 出现在 449/615/671 行。其中多数是标准库，无延迟加载必要。
**修法**：标准库 import 全部上提模块顶层；只有 `astrbot.api.message_components`、`MessageChain` 这类随框架版本可能变的，可保留局部但加注释说明原因。

### B3 配置分组取值模式重复（已验证）
```python
sec = self.config.get("sticker") if isinstance(self.config, dict) else None
sec = sec if isinstance(sec, dict) else {}
```
该三行在 175-176、215-216、255-256 重复三次；同型逻辑又在 `_favour_cfg`(286-288)、`_poke_cfg`(341-342)、`_proactive_cfg`(543-544) 各写一遍。
**修法**：统一为 `def _sec(self, name: str) -> dict`，六处全部改调用。

### B4 token 诊断三处路径拼接重复（推测）
`_tok_path`(803) / `_proactive_path`(546) 等各自 `os.path.join(self._data_dir(), ...)`。
**修法**：`_data_dir` 旁加 `_data_file(name)`。

## C. 臃肿

### C1 `main.py` 单类 40 方法（已验证）
`TuhengyuPlugin` 同时承担：生命周期（initialize/terminate）、表情包三职（attach/separate/collect）、好感度两职（inject/collect）、戳一戳（on_poke 及 4 个私有）、主动插话（watch/_text/_maybe/test）、token 诊断（7 个 `_tok_*`）、命令（status/test_moment/favour_status/token_diag）、10 个 Web API、设置读写（6 个）。
**修法（建议拆法）**：
```
main.py                  → 只留 Star 子类：__init__/initialize/terminate + 注册
handlers/sticker.py      → attach/separate/collect + 私有
handlers/favour.py       → inject/collect + _scope
handlers/poke.py         → on_poke + _poke_text/_poke_touch/_send_poke
handlers/proactive.py    → watch_group/_proactive_*/test_proactive
web/routes.py            → 10 个 page_*
web/settings.py          → _load_schema/_coerce/_merge_settings/_collect_options/_config_values
diag/token.py            → _tok_* 全部 + token_diag
```
目标：`main.py` ≤ 200 行。此改动大，会动 import 与注册顺序，建议单独一个版本做，不做混合提交。

### C2 10 个 Web API 挤在 main.py（已验证）
`page_status` … `page_settings_post`（1019-1367，约 350 行）与业务逻辑无关，纯路由。
**修法**：并入 C1 的 `web/routes.py`。

### C3 设置读写约 130 行可独立（已验证）
`_load_schema`/`_config_values`/`_coerce`/`_merge_settings`/`_collect_options`（1234-1333）是一个自洽小模块。

## D. 面向客户不友好

### D1 插件 README 严重过期（已验证，最高优先）
`README.md` 开头写「版本：0.2.7」「第一版：作息 + 调度器 + 发 QQ 空间」，正文只覆盖调度器与发空间。而实际 0.2.27 已有：私聊/群聊增强、表情包（附带/单独/收集/识图分类）、好感度、戳一戳、主动插话、Web 控制台、token 诊断。
读者按 README 会以为插件只有发空间功能。
**修法**：重写 README，按六项行为 + 控制台 + 配置说明组织；版本号与 `metadata.yaml` 同步维护。

### D2 metadata.yaml 描述过期（已验证）
`metadata.yaml:3` desc 仍是「第一版：调度器 + 发 QQ 空间（内容由模型生成）」。插件市场/列表里显示的就是这一行。
**修法**：改为覆盖现状的一句话，例如「给 bot 完整的一生：作息驱动 + 发空间 + 表情包 + 好感度 + 戳一戳 + 主动插话」。

### D3 LICENSE 待定（已验证）
README 写「许可：待定」。对分发起副作用：别人不能确定能否用。
**修法**：与项目整体 LICENSE 一并定（待博士拍板）。

### D4 安装步骤与目标读者不符（已验证）
README 安装用 `git clone` + `cp -r` + `docker restart`。但项目定位是「面向零基础一键操作」，且目标 VPS 实测**无 git、无 curl**。零基础用户照抄会卡在第一步。
**修法**：改为「面板一键部署」为默认路径，git 手动装降为「进阶 / 备用」。

### D5 占位路径未落实到具体目录（已验证）
README 写 `<AstrBot数据目录>/plugins/`，未给常见默认路径（本项目实测为 `/AstrBot/data/plugins/`）。零基础用户会在此处迷路。
**修法**：补一行「Docker 部署通常就是 `/AstrBot/data/plugins/`」。

### D6 配置默认值方向易误解（推测）
`proactive.enabled` 默认 `false`、`_conf_schema.json:307` 的 `hint` 缩进比同级多一级（格式小瑕疵，不影响解析）；`sticker.collect_enabled` 默认 `true`，即默认会往群里存别人的图，新用户可能不希望。
**修法**：`proactive` 保持默认关（合理）；`collect_enabled` 在 hint 里明确「默认开，会占用磁盘」，或改默认关。

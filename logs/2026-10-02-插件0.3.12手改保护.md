# 插件 0.3.12：手改印象/关系的保护 + 一次 schema 翻车（2026-10-02）

## 结论

博士反馈「印象和关系也会被覆盖，疑似更改无效」。查证结果：**写入链路没问题**，
是模型每轮把这两个字段**重新写了一遍**（它们是自由文本，注入里没有「照抄」的硬约束）。
本轮加三层保护，并修掉过程中自己踩的一个坑：`_conf_schema.json` 用了不支持的 type，导致插件整个加载失败。

## 一、为什么印象/关系特别容易被改写

- `build_injection` 要求模型每轮在末尾输出 `%%FAV%% 好感 | 印象 | 关系`；
- 好感度有硬约束（「写绝对值」「即使没变化也要照写当前值」），且数值改动幅度由曲线限定；
- **印象与关系没有同等约束**——模型把它们当成「每轮重新生成的描述句」，于是换措辞、换说法；
  手感上就是「我改的又被改回去了」。
- 叠加 0.3.11 之前的老问题（历史里残留状态行 → 模型照抄），表现得更像「改了没用」。

## 二、修法

1. **注入里收紧口径**（`build_injection`）：
   「印象与关系尤其要逐字照抄上面给出的当前值，不要换措辞、不要润色；只有当本轮确实出现了新的实质互动
   （关系转折、明确表态）时才改写它们。」
2. **手改保护**（`FavourStore` + `handlers/favour.py`）：
   - 页签保存时，被手改过的文本字段记入 `manual_at` / `manual_fields`；
   - 回收状态行时（`collect_favour`）先算 `manual_hold(key, hours)`，窗口内**忽略模型对这两个字段的改写**
     （好感度不受限——它本来就该随互动走），并记一条 INFO 日志；
   - 窗口长度：新配置项 `manual_hold_hours`，默认 **24** 小时，`0` = 关闭；
   - 页签上显示「🔒 印象/关系锁定至 YYYY-MM-DD HH:MM」，并给一个「解锁」按钮
     （`favour-update` 加 `clear_hold` 分支）。
3. **时间戳只在真变化时刷新**（`FavourStore.update`）：
   以前每轮都写 `updated_at`，看不出「谁最后改的」。现在值没变就不写盘。
   于是「手改后时间戳不再跳动」本身就是没被覆盖的证据。

## 三、翻车记录：`"type": "number"`

- 给 `manual_hold_hours` 写 schema 时用了 `"type": "number"`。
- AstrBot 的 `_config_schema_to_default_config` 只认
  `int / float / bool / string / text / list / file / object / template_list / dict`，
  遇到 `number` 在 `_parse_schema` 里直接 `TypeError`。
- **后果**：插件**整体加载失败**。日志表现极具误导性——只有一整串
  `Removed module data.plugins.astrbot_plugin_tuhengyu.*`，`grep tuhengyu` 只看得到这些，
  很容易误判成"只是重载了一次"。真正的报错在 `star.star_manager:1437 ----- Failed to load plugin -----` 之后。
- **修法**：`number` → `int`，重新部署，日志确认 `Plugin astrbot_plugin_tuhengyu (0.3.12)` + 调度器启动。
- **防复发**：新增 `scripts/lint_conf_schema.py`（JSON 合法性 + type 白名单），改完 schema 先跑。
  另记：判断插件是否真的加载成功，**不要看 Removed module 那几行**，要 grep
  `Plugin .* \(0\.3\.` 与 `生活调度器已启动`，或 grep `Failed to load`。

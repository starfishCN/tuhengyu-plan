# 2026-10-01 插件 0.2.5：人设来源改为读 AstrBot 人格 + 下拉配置

## 起因

用户两点：
1. **体验**：配置项凡能从候选中选一的（大模型商家 / provider、人格 / persona 等）都改成**下拉选择**，别手填。
2. **Bug 反馈**：「换上人格之后，webui 未检测到」。

## 一、根因（第 2 点）

插件此前的人设**只有一条来源** —— 插件配置里的 `persona_prompt`（一段手写文本），出现在 `core/llm.py:64`、`core/schedule.py:110`、`core/scheduler.py:175`、`_conf_schema.json:8`。

博士在 AstrBot 的「人格」里换人格，与插件无关，插件自然「检测不到」。

**修正方向**：把插件人设来源改成**读 AstrBot 的人格** —— 默认跟随 AstrBot 当前默认人格（换人格自动跟上），也可在插件配置里用下拉单独指定一个。`persona_prompt` 从「唯一来源」降级为「可选补充」。

### 依据（在容器内读 AstrBot 源码）

- `context.persona_manager`（`/AstrBot/astrbot/core/star/context.py`）→ `PersonaManager`（`/AstrBot/astrbot/core/persona_mgr.py`）。
  - `get_persona_v3_by_id(pid)`：空 id → `None`；`"default"` → 内置 `DEFAULT_PERSONALITY`；否则在 `personas_v3` 里按 **name**（非 id）匹配。
  - `async get_default_persona_v3(umo=None)`：读 `agent_runner.config.persona.persona_id`，取不到回落 `DEFAULT_PERSONALITY`。
  - `Personality` 是 TypedDict（`/AstrBot/astrbot/core/db/po.py:592`），含 `prompt`、`name` 等键。

## 二、下拉配置（第 1 点）

AstrBot 的 `_special` 字段让配置项渲染为专用控件，官方已支持：`select_provider` / `select_provider_stt` / `select_provider_tts` / `select_providers` / `select_persona` / `select_knowledgebase` / `select_plugin_set` / `t2i_template` / `agent_runner_type` 等（见 `core/config/default.py`，前端实现散落在 `dashboard/dist/assets/*.js`）。

插件侧填 `_special` 即自动获得下拉，无需自写前端。

- 新增：`persona_id`（`type: string`、`_special: select_persona`、默认空 = 跟随默认）。
- 既已为下拉：`chat_private.model`、`chat_group.model`、`schedule.generate_model`、`moment.provider_id`（均 `select_provider`）。
- **面板自身（NiceGUI）不做这些下拉** —— 面板只做部署，插件配置由 AstrBot 按其 `_conf_schema.json` 自动渲染。

### 人设来源优先级（定案）

① 插件配置 `persona_id` 指定的人格 → ② 否则跟随 AstrBot 当前默认人格 → ③ 再叠加插件配置 `persona_prompt`（补充文本，可选）→ ④ 都没有则空串，回落内置 `DEFAULT_SYSTEM_PROMPT`。

### 收尾修正（同一轮）

- 失败原因透出：`Schedule` 新增 `_last_error` / `last_error()`，`_fallback()` 记原因，`ensure()` 各成功分支清空；`scheduler.status_dict()` +`schedule_error`；页面 `persona-note` 增「人设已读到但作息没生成成功（原因）」分支。

## 补记：0.2.6「测试发一条」按钮无反应

### 反馈

博士点开页面后：「测试发一条」按钮按下去没反应。

### 根因（已从 AstrBot 源码证实）

插件页跑在 AstrBot 的**受限 iframe** 里。前端 dist 里：

```
class:"plugin-page-frame", referrerpolicy:"no-referrer",
sandbox:"allow-scripts allow-forms allow-downloads"
```

**sandbox 里没有 `allow-modals`。** 按 HTML 规范，在缺 `allow-modals` 的 sandbox iframe 里，`window.confirm()` / `alert()` / `prompt()` 会被浏览器**静默忽略**，`confirm()` 直接返回 `false`（控制台报 `Ignored call to 'confirm()'`）。

而「测试发一条」正是页面上**唯一**用了 `window.confirm` 的地方：

```js
const ok = window.confirm("这会真的往 QQ 空间发一条动态。确定要继续吗？");
if (!ok) return;   // ok 恒为 false → 直接返回 → 什么都不发生
```

「重算作息」没用 confirm，所以正常 —— 症状完全吻合。

顺带验证了 bridge 的加载顺序不是问题：bridge-sdk 由服务端以**经典 script** 注入在 `</body>` 前（`plugin_page_service.py:741`），经典脚本在解析期执行，早于 `type="module"` 的 app.js（模块默认 defer，解析完才跑），故 `window.AstrBotPluginPage` 在 app.js 运行时已存在。

### 修法（0.2.6）

改用**页内两步确认**，不依赖 `window.confirm`：

- 第一次点「测试发一条」→ 按钮文案变「再点一次确认发送」+ notice 提示；8 秒不点自动还原。
- 第二次点才真正 `apiPost("test-moment")`。
- `disarmTest()` 负责还原文案与清定时器。

另加一处防御：`bind()` 里 `bridge.onContext?.(…)` → `bridge?.onContext?.(…)`，避免 bridge 缺失时抛错中断后续绑定。

### 部署与验证

- 版本 `metadata.yaml` / 插件 README → 0.2.6。
- 打包 26248 字节，双副本 rsync 覆盖，备份 `/root/backup_plugin_20261001_201146`。
- 容器内 `node --check app.js` → NODE_OK；重启日志 `Plugin astrbot_plugin_tuhengyu (0.2.6)`。
- 重启日志另见 `作息：读盘（7 段）` —— 盘上已有生成好的作息（此前为 conservative 2 段），说明期间已在 AstrBot 配好模型并生成过作息。
- 推送 `d51855f..b7d58e4`。

### 知识点（新增，必读）

**插件页 iframe 的 sandbox = `allow-scripts allow-forms allow-downloads`** → 无 `allow-modals`、无 `allow-same-origin`。因此：
- `alert` / `confirm` / `prompt` **不可用**，需自实现页内确认。
- 页面处于**不透明源**（无 allow-same-origin），不要依赖 localStorage / cookie / 同源直连接口；跨页面通信走 bridge。

## 补记：0.2.7 手动发说说丢人设（老问题复现）

### 反馈

博士：「空间说说不带人设。犯老问题了。」（指当初给 `qzone_ultra` 打人格补丁时那类坑）

### 根因

`main.py` 的 `_publish_once()`（`/图恒宇测试` 与页面「测试发一条」共用）调用：

```python
content = await generate_moment_text(self.context, self.config, st.now_line())
```

**漏传 `persona`**。而 `core/llm.py` 里：

```python
system_prompt = persona or config["persona_prompt"] or DEFAULT_SYSTEM_PROMPT
```

插件改造后人设来自 AstrBot 人格，`config["persona_prompt"]` 为空 → 落到 **DEFAULT_SYSTEM_PROMPT** → 说说不带人设。

自动调度路径 `scheduler.maybe_moment()` 是传了的（`self.persona_text`），所以**只有手动那条不带** —— 与现象吻合，也与旧补丁「非 event 路径丢人格」属同一类错。

### 修法（0.2.7）

```python
content = await generate_moment_text(
    self.context, self.config, st.now_line(), self._scheduler.persona_text
)
```

`_publish_once` 在调用前已 `await self._refresh_persona()`，故 `persona_text` 是当前值。

复核：全仓 `generate_moment_text` 仅两处调用 —— `scheduler.maybe_moment`（已传）、`main._publish_once`（本次补上）。

### 部署踩坑：rsync 静默跳过同名同长度文件

`0.2.7` 第一次部署后，`main.py` 已更新（含修复），但 `metadata.yaml` 仍是 `0.2.6`。

原因：`rsync -a` 默认用 **size + mtime** 做 quick check。`0.2.6` → `0.2.7` **字节数相同**，且经 Android FUSE/tar 往返后 mtime 被判为一致 → rsync 直接**跳过**该文件。

处置：改用 **`rsync -aI --delete`**（`-I` = `--ignore-times`，强制传输）。此后双副本与容器内均为 `0.2.7`。

**纪律：本项目的部署命令一律带 `-I`，否则同名等长文件会被静默跳过。**

# 09 · 常见问题

本篇收录错题本 E01–E16。先看现象，再按对应处理。不要连续重复点击部署按钮，也不要看到半截日志就重装。

## 一、先收集信息

面板任务失败时，只处理日志最后一条带 `!!` 的提示。需要反馈时，附上最后 20–80 行完整日志，不要只写「报错了」。

```bash
systemctl status tuhengyu-panel --no-pager
docker ps -a
docker logs --tail 100 astrbot
docker logs --tail 100 snowluma
```

如果面板本身打不开，再执行：

```bash
journalctl -u tuhengyu-panel -n 80 --no-pager
```

不要附 SSH 密码、API Key、Token、Cookie 或完整凭据日志。

## 二、拉不下安装脚本：E01–E03

### 1. Gitee raw 返回 451

**现象：**访问 Gitee 的 `.sh` raw 地址返回 HTTP 451；同仓库的 `README.md`、`main.py` 可能仍返回 200。

**原因：**Gitee 会对 `.sh` 文件的 raw 下载触发风控。把文件从 `install.sh` 改名为 `setup.sh` 不能保证绕过。

**处理：**使用项目 README 中的多源引导命令。当前顺序是 jsDelivr → GitHub raw → Gitee raw，并且入口会先尝试补齐 `curl`、`wget` 或 `python3`。不要手动拼 Gitee API 请求。

### 2. Gitee API 报 `list indices must be integers or slices, not str`

**现象：**脚本中出现类似：

```text
TypeError: list indices must be integers or slices, not str
```

**原因：**请求的文件路径不存在时，Gitee API 返回目录列表；代码却把返回值当成包含 `content` 字段的文件对象。最常见原因是仍请求旧文件名 `install.sh`，实际文件已改为 `setup.sh`。

**处理：**不要继续使用旧命令。重新从 README 复制整段最新版引导命令，确认路径和文件名来自当前仓库。

### 3. 命令仍指向 `install.sh`

**现象：**朋友转来的旧命令或旧教程访问 `install.sh`，但仓库只有 `setup.sh` 或 `bootstrap.sh`。

**处理：**使用根 README 的快速开始命令。旧命令不要只改其中一处，避免脚本名、raw 地址和 API 路径不一致。

## 三、安装环境问题：E06–E08

### 4. 安装脚本提示目标目录已存在

**这是保护，不是故障。**新版脚本发现 `/opt/tuhengyu-panel` 已存在但不是图恒宇计划仓库时，会停止并保留原文件，不会覆盖。

处理方式：

```bash
TUHENGYU_DIR=/opt/tuhengyu-panel-new bash setup.sh
```

或者先确认旧目录确实属于本项目，再备份后处理。不要直接执行 `rm -rf /opt/tuhengyu-panel`。

旧版本曾经在源码回退失败时删除正式目标目录，导致后续 clone 因当前工作目录消失而失败。新版已改为先下载到临时目录，成功后再移入。

### 5. `ensurepip is not available`

**现象：**创建 Python 虚拟环境失败，出现 `ensurepip is not available`。

**原因：**Ubuntu 最小化系统缺少 `python3-venv`，不一定是 Python 主程序损坏。

**处理：**当前 `setup.sh` 会自动补装 `python3-venv` 并重试。若自动安装失败：

```bash
apt-get update
apt-get install -y python3-venv
```

然后回到面板重新执行失败步骤。不要直接删除整个项目目录。

### 5. pip 报 `Network is unreachable` 或 `Errno 101`

**现象：**pip 连接 PyPI 失败，日志出现网络不可达。

**原因：**服务器没有国际出口，与 Docker Hub 拉取失败通常是同一类网络问题。

**处理：**新版脚本会依次尝试 PyPI、清华、阿里和中科大源，并带超时与有限重试。若仍失败，换国内线路、配置代理或使用可达的服务器。不要无限重复 pip 命令。

### 6. Docker Hub 返回 000、Cloudflare 超时：E08

**现象：**请求 Docker Hub `/v2/` 返回 000，或镜像开始下载后在 Cloudflare/CDN 阶段超时；换一个公共加速地址仍失败。

**原因：**registry 入口可达不代表镜像分层文件的 CDN 可达。

**处理：**面板会先安装 Docker，再测速并应用可用镜像源。全部源不可用时，换服务器线路、为 dockerd 配置代理，或通过另一台能联网的机器 `docker save` / `docker load` 转移镜像。

## 四、镜像源与镜像拉取：E09–E11

### 7. 镜像源返回 403 却被选中：E09

**现象：**镜像源测速显示可用，但实际 `docker pull` 失败；源的 HTTP 响应是 403。

**原因：**旧探测逻辑把所有低于 500 的状态码都当成可用，错误地把 403 纳入候选。

**当前规则：**2xx、3xx 和 401（registry 正常的鉴权挑战）才算可用；403 视为不可用。若日志仍显示选中了 403，说明运行的不是当前面板版本，应先更新面板。

### 8. 镜像源列表中的地址失效：E10

**现象：**某些旧教程推荐的中科大、网易或 rainbond 地址不可达，测速长期超时。

**处理：**不要逐个手动尝试旧列表。使用当前面板的自动测速结果。失效地址已从主要候选中移除，并保留可继续探测的候选。全部不可用时按 E08 换线路或配置代理。

### 9. AstrBot 镜像拉取失败：E11

**现象：**`docker pull soulter/astrbot:latest` 在无国际出口服务器上失败。

**处理：**当前部署流程包含 DaoCloud 兜底：尝试 `m.daocloud.io/docker.io/` 前缀拉取，再用 `docker tag` 恢复本地镜像名。该兜底尚需完整真机验证；如果仍失败，保留最后完整日志，不要自行改容器名和镜像标签。

### 10. SnowLuma 大镜像拉取失败：E18

**现象：**Docker 本身安装成功，镜像代理能显示 `Pulling from` 或返回 manifest，甚至有一层显示 `Download complete`，但后续 blob 从 Cloudflare/CDN 下载时超时。

**原因：**registry/manifest 和镜像分层文件可能走不同域名。入口能访问，不代表完整镜像能下载。

**处理：**不要把“能返回 manifest”当成镜像源可用。以完整 `docker pull` 成功为准。公共前缀连续失败时停止反复切换，选择以下方案之一：

1. 为 Docker daemon 配置实际可用的代理。
2. 在能完整联网的机器执行 `docker pull motricseven7/snowluma:latest`，再执行 `docker save -o snowluma.tar motricseven7/snowluma:latest`。
3. 把 tar 文件上传到服务器，执行 `docker load -i snowluma.tar`。
4. 确认 `docker images motricseven7/snowluma` 存在后，再重新执行 SnowLuma 部署步骤。

不要删除 Docker 数据目录、已有数据卷或 SSH 配置。已下载的层可以保留，失败日志也要保留。

## 五、面板和密码：E13–E14

### 11. 安装完成输出与旧教程不一致：E13

**当前新装成功的结果：**终端会显示面板地址、账号和随机初始密码，例如：

```text
面板地址：http://服务器IP:8080
账号：admin
初始密码：一串随机字符
```

浏览器使用 `admin` 和该密码登录。首次登录会强制修改密码。旧教程中直接给固定启动命令或固定密码的截图已经过时。

### 12. 新旧面板密码口径不同：E14

**新装实例：**随机生成初始密码，首次登录强制改密。

**旧实例：**可能仍使用旧版固定密码或旧认证文件。不要用新装口径覆盖旧实例，也不要为了找回密码直接删除数据目录。先备份认证文件，查看 systemd 配置、面板日志和当前部署版本。

### 13. 面板打不开

按顺序检查：

1. 地址使用 `http://`，不是 `https://`。
2. 云服务器安全组放行面板外部端口 8080。
3. `systemctl status tuhengyu-panel` 是否为 `active`。
4. `journalctl -u tuhengyu-panel -n 80 --no-pager` 的最后错误。

## 六、真小白流程问题：E15–E16

### 14. 安装失败后不知道该做什么：E15

当前正确流程不是让用户自己判断 Python、venv、pip 和 Docker 源：

1. 只执行 README 的多源入口命令。
2. 登录面板。
3. 只点击「开始自动部署」。
4. 失败时只看最后一条 `!!`，按本篇对应条目处理。
5. 修复网络或环境后，再点击同一个主按钮。

基础工具、`python3-venv`、pip 镜像和 Docker 镜像源均已纳入自动处理。不要同时点多个单步按钮。

### 15. 面板暴露太多开发步骤：E16

普通用户不需要理解以下安装关系：Docker → 镜像源 → AstrBot → SnowLuma → 插件。它们由「开始自动部署」按固定顺序执行。

「高级模式：单独执行步骤」只用于排错。除非日志明确要求，不要从高级模式开始，也不要跳过前置步骤直接安装插件。

## 七、权限和测试环境：E12

### `/sdcard` 上 `chmod 600` 测试失败

**现象：**认证文件权限测试显示 660 或其他结果，但同一代码在 `/tmp` 能得到 600。

**原因：**安卓 `/sdcard` 通常是 FUSE 挂载点，不保留标准 POSIX 权限位。

**结论：**这是本机测试环境限制，不代表 VPS 上的面板权限失效。VPS 部署应在 Linux 文件系统中验证。不要为了通过 `/sdcard` 测试修改业务代码。

## 八、NAT、端口与安全

### NAT 机器浏览器打不开

NAT VPS 需要区分两个端口：

- 内部端口：程序在服务器里监听的端口。
- 外部端口：服务商分配给你，浏览器或 SSH 实际访问的端口。

例如外部 `18080` 转发到内部 `8080`，访问地址必须是：

```text
http://公网IP:18080
```

不是：

```text
http://公网IP:8080
```

安装前就要向服务商确认端口映射：

| 用途 | 内部端口 | 是否必须映射 | 说明 |
|---|---:|---|---|
| SSH | 22 | 必须 | 没有它无法连接服务器 |
| 面板 | 8080 | 必须 | 浏览器打开外部映射端口 |
| noVNC | 6081 | 必须 | 扫码登录 QQ 时使用 |
| SnowLuma 控制台 | 5099 | 可选 | 需要查看控制台时映射 |
| AstrBot 控制台 | 6185 | 可选 | 需要配置模型时映射 |
| OneBot 内部通信 | 6199 | 禁止 | 只允许容器内部使用 |

端口映射正确但仍打不开时：

1. 确认浏览器使用的是外部端口。
2. 确认服务商的映射目标是对应内部端口。
3. 确认云安全组或 NAT 防火墙放行外部端口。
4. SSH 执行 `ss -lntp`，确认程序确实监听内部端口。
5. 不要因为 `8080` 打不开就重复安装面板。

### 端口与安全

| 端口 | 用途 | 建议 |
|---|---|---|
| 8080 | 部署面板 | 测试时开放，长期限制来源 |
| 6081 | noVNC | 只在扫码时开放 |
| 5099 | SnowLuma 控制台 | 限制来源 |
| 6185 | AstrBot 控制台 | 限制来源 |
| 6199 | 容器内部通信 | 不映射公网 |

E05 记录的公开仓历史凭据属于安全问题，不是安装排错。使用过的 SSH 密码、面板密码、API Key 和 Token 都应轮换；不要把新的凭据写进日志或公开仓。

## 九、彻底重试前的检查

只有确认需要全新测试时，才清理容器和数据卷。普通安装失败先保留现场：

```bash
docker ps -a
docker images
docker volume ls
docker logs --tail 100 astrbot
docker logs --tail 100 snowluma
```

面板任务结束后才能重试。不要并行点击。重试仍失败时，附上操作步骤、系统版本、架构、面板最后 20 行和相关容器日志。
